# UpCheck

**모집 안내문을 기준으로 제출 PDF의 누락·중복을 점검하고, 보완 답장까지 이어서 확인하는 관리자 웹앱입니다.**

극락쿼카 팀의 제출서류 사전 점검 프로젝트입니다. Upstage Studio가 문서를 읽고 판정하며, Google Apps Script가 Gmail 접수, 관리자 화면, HTML 보완 안내, 재시도와 처리 이력을 연결합니다.

현재 GitHub 저장소는 **비공개**입니다. 저장소 열람과 복제에는 권한이 필요하며, 아래 웹앱·Studio의 접속 권한과는 별개입니다.

> 점검 결과는 **PDF 내용의 사전 점검**입니다. HWP/HWPX 원본 내용 일치, 서명 진위, 지원 자격, 최종 접수·선발을 확정하지 않습니다. 실제 개인정보를 처리하기 전에 기관의 적법한 처리 근거와 외부 AI 전송 범위를 확인해야 합니다.

외부 계정에서 **Unverified / Authorization needed** 화면이 나올 수 있습니다. 주소 변경으로 Google 앱 검증을 대신할 수 없습니다. 각 관리자의 화면에는 자기 계정의 설정·기록만 표시되므로, 다른 사람이 링크를 열어 기존 관리자의 시연 기록을 보는 방식도 아닙니다. 외부 계정 전체의 권한 연결 성공을 검증한 상태는 아닙니다. 자세한 조건은 [Google 공식 안내](https://developers.google.com/apps-script/guides/client-verification)를 확인하세요.

이 웹앱 URL은 소스 실행 안내용으로 기록했습니다. 별도 제출 ZIP에는 웹앱 링크 파일과 데모 영상을 포함하지 않았습니다. 영상은 이 저장소에 업로드하지 않았습니다.

## 주요 기능

- 안내문에서 팀별·팀원별 제출 조건을 읽어 필수 서류와 예상 제출 수를 대조합니다.
- PDF의 문서 유형, 작성자, 접수번호를 기준으로 누락·중복·불명확한 서류를 구분합니다.
- 확정된 누락·중복은 HTML 메일로 원 제출자에게 안내합니다. 이름은 일부 가립니다.
- 불명확한 작성자, 다른 접수번호, 읽기 어려운 서명 등은 **담당자 확인**으로 보류합니다.
- 같은 대화에 보완 답장이 오면 기존 첨부와 합쳐 다시 점검합니다.
- 계정별 설정·API 키·접수 기록과 사용자 잠금을 사용합니다.
- 일시적 오류를 제한적으로 재시도하며, 발송 여부가 불명확한 메일은 자동으로 다시 보내지 않습니다.

## 처리 흐름

```text
관리자: Google 로그인 → 본인 메일·API 키·안내문 저장 → 자동 점검 시작
제출자: 제목 [서류체크 실험]으로 PDF 메일 제출
        ↓
Gmail 접수 → PDF 업로드 → Upstage Studio #14 실행
        ↓
Parse → Classify → Extract × 3 → Merge → Instruct
        ↓
내용 완비 / 보완 요청 / 담당자 확인
        ↓
확정 누락·중복만 HTML 보완 안내 → 답장 첨부 → 누적 서류 재점검
```

AI가 문서 판정을 만들고, 앱은 결과 형식 검증·메일 대상 제한·발송 제어를 담당합니다. 앱이 정답지에 맞춰 AI 결과를 바꾸거나 누락·중복을 별도로 재계산하지 않습니다.

## 빠른 실행

### 1. 소스와 로컬 검증

Node.js 18 이상과 Git이 있으면 실행할 수 있습니다. 별도 npm 패키지 설치는 필요하지 않습니다.

```bash
git clone https://github.com/chominseo0723/UpCheck.git
cd UpCheck
npm test
npm run check:build
```

`npm test`는 배포 파일을 생성하고 4개 모의 검증을 실행합니다. Gmail이나 Upstage API에 실제로 접속하거나 메일을 보내지 않습니다. 로컬 검증 통과는 실서비스 전체 경로의 성공을 보장하지 않습니다.

### 2. Apps Script에 배포

1. [Google Apps Script](https://script.google.com/home)에 관리자 본인 계정으로 새 프로젝트를 만듭니다.
2. 기본 `Code.gs` 내용을 **[build/Deploy.gs](build/Deploy.gs)** 전체로 교체합니다.
3. 프로젝트 설정에서 매니페스트 표시를 켜고 **[build/appsscript.json](build/appsscript.json)** 내용을 적용합니다.
4. `배포 → 새 배포 → 웹 앱`을 선택합니다. **실행 사용자: 웹 앱에 액세스하는 사용자**로 설정합니다.
5. 필요한 관리자에게 맞는 접속 범위를 선택하고, 발급된 `/exec` 주소로 접속합니다. 다른 Google 계정까지 허용하는 배포는 그 범위에 대한 운영자 판단과 기관 정책 확인이 필요합니다.

`Deploy.gs`에는 Core·서버 코드·HTML이 합쳐져 있습니다. **통합 파일을 붙여 넣은 프로젝트에 `src/Core.js`, `src/Code.gs`를 추가로 복사하지 마세요.** 상수와 함수가 중복됩니다. 상세 단계와 별도 워크플로우 연결은 [설치 안내](docs/SETUP.md)에 있습니다.

### 3. 관리자 연결

1. 점검할 Gmail/Google Workspace 계정으로 로그인합니다.
2. Google이 표시하는 요청 권한을 직접 확인하고 계정 연결을 진행합니다. 미검증 앱·기관 차단 화면이 나오면 [접속 제한 안내](docs/TROUBLESHOOTING.md#google-미검증-앱-또는-접속-차단)를 확인합니다.
3. **관리자 수신 이메일**에 현재 로그인한 계정과 같은 주소를 입력합니다. 다른 주소만 입력해서 그 받은편지함을 연결할 수는 없습니다.
4. Studio 연결 설정에 해당 워크플로우를 실행할 권한이 있는 **본인 Upstage API 키**를 입력합니다. 별표로 가려진 문자열은 사용할 수 없습니다.
5. 모집·제출 안내문을 붙여 넣습니다. 예제는 [examples/notice.txt](examples/notice.txt)에 있습니다.
6. 개인정보 처리 안내와 원문 AI 전송 범위를 확인하고 설정을 저장합니다. 이 확인은 기관의 적법한 처리 근거를 대신하는 동의서가 아닙니다.
7. 시험 실행은 자동 안내 체크를 해제한 상태로 시작할 수 있습니다. 실제 발송을 원하면 체크한 뒤 저장합니다.
8. **자동 점검 시작**을 누릅니다. 이후 새 메일을 5분 주기로 확인하며, **지금 확인**으로도 진행할 수 있습니다.

다른 관리자가 사용하려면 그 관리자 본인 계정으로 위 절차를 진행해야 합니다. 저장된 API 키·접수 기록을 다른 계정과 공유하지 않습니다. API 키는 소스, README, 스크린샷, GitHub에 올리지 않습니다.

### 4. 제출·보완 시험

관리자 계정과 **다른 발신 계정**에서 메일을 보냅니다. 관리자 본인이 자기 자신에게 보낸 메일은 처리하지 않습니다. 설정 저장 시점보다 이전 메일은 신규 접수 대상이 아닙니다.

| 항목 | 값 |
| --- | --- |
| 받는 사람 | 웹앱에 연결한 관리자 본인의 수신 주소 |
| 제목 | `[서류체크 실험] 정상 서류 확인`처럼 **정확한 접두어**로 시작 |
| 첨부 | PDF. 한 접수에서 누적 PDF 최대 12개·합계 20MB |
| 보완 | 기존 안내 메일에 **답장**으로 PDF 첨부. `Re:`는 허용 |

제목 접두어는 `[서류체크 실험]`으로 유지합니다. `[서류점검 체크]` 등 다른 문구는 처리 대상이 아닙니다.

| 예제 | 보낼 PDF | 기대 동작 |
| --- | --- | --- |
| 정상 A | [정상팀](examples/01_정상팀_제출서류.pdf) | 필수 6부 확인 → PDF 내용 완비 |
| 누락 B | [누락팀](examples/02_누락팀_제출서류.pdf) | 박지민 동의서 누락 → 보완 안내 또는 미리보기 |
| B 보완 | [B용 박지민 동의서](examples/04_누락팀_보완_박지민동의서.pdf)를 **B 대화에 답장** | 누락 보완 후 재점검 |
| 중복 C | [중복팀](examples/03_중복팀_제출서류.pdf) | 김하늘 동의서 중복·박지민 동의서 누락 → 보완 안내 또는 미리보기 |
| C 보완 | [C 전용 답장 보완 폴더](examples/중복건_답장보완용)의 PDF 두 개를 **C 대화에 함께 답장** | 중복 묶음 교체 + C용 동의서 추가/교체 후 재점검 |

예제의 이름·학번·연락처·서명은 가상값입니다. B용 동의서를 C 접수에 사용하면 접수번호가 달라 **담당자 확인**으로 보류될 수 있습니다.

**보완 파일명 규칙**

- 같은 대화·발신자·제목의 보완 파일을 누적합니다.
- **같은 파일명**을 다시 보내면 해당 파일의 최신 버전으로 교체합니다.
- **다른 파일명**은 기존 서류에 추가합니다. 기존 묶음 안의 중복 페이지는 저절로 없어지지 않습니다.
- 한 메일에 같은 이름의 파일을 두 개 첨부하면 둘 다 보존해 중복 점검 대상에 포함합니다.
- C 전용 보완 두 파일은 **파일명을 바꾸지 않고** 첨부해야 기존 잘못된 묶음·B 동의서를 교체할 수 있습니다.
- 결과 목록의 이전 행은 이력입니다. 보완 완료 여부는 최신 `Re:` 행에서 확인합니다.

## 결과 상태 읽기

| 화면 상태 | 의미 | 자동 안내 |
| --- | --- | --- |
| 첨부 업로드 중 | PDF 업로드·실행 접수 중 | 결과 확인 전 대기 |
| AI 점검 중 | 실행·결과 조회 중 | 결과 확인 전 대기 |
| 자동 재시도 대기 | 일시적 오류 후 재개 예약 | 아직 발송하지 않음 |
| 안내 미리보기 | 누락·중복 확정, 자동 안내 꺼짐 | 발송하지 않음 |
| 보완 안내 발송 | 확정된 누락·중복 안내 완료 | 원 제출자에게 회신 |
| PDF 내용 완비 | 안내문 기준 PDF 내용 점검상 필수 서류 확인 | 완료 알림 메일은 보내지 않음 |
| 담당자 확인 | 불명확한 문서·서명·접수번호 또는 복구 한도·권한 문제 | 자동 발송 보류 |
| 보완 메일로 대체됨 | 최신 보완 메일이 생겨 이전 건 처리를 중단 | 이전 결과 추가 발송 생략 |

`PDF 내용 완비`는 최종 접수 완료나 선발 승인이 아닙니다. 예를 들어 `format_status: 원본 확인 필요`는 별도 HWP 원본 확인이 남았다는 의미이며, 그것만으로 확정된 누락 안내를 항상 막지는 않습니다. 서명 진위는 이 앱의 판정 범위가 아닙니다.

## 저장소 구성

```text
src/         Core.js, Code.gs, Index.html, appsscript.json 원본
build/       Apps Script에 복사할 통합 Deploy.gs와 매니페스트
scripts/     배포 파일 생성 스크립트
tests/       발송 제어·개인정보·장애 복구·설정 저장 모의 검증
workflow/    Studio 최종 #14 실제 내보내기 JSON
evaluation/  평가용 PDF 8개, 정답지 JSON, 유형표
examples/    가상 메일 시연 PDF와 B/C 보완용 파일
docs/        설치, 개인정보 처리, 문제 해결, 검증 범위
```

일반적인 코드 수정은 `src/`에서 하고 `npm run build`로 통합 파일을 다시 만듭니다. `build/Deploy.gs`만 직접 수정하면 다음 빌드 때 덮어써집니다. 재배포 시 Apps Script의 **새 버전**을 기존 배포에 적용해야 기존 `/exec` URL이 새 코드를 사용합니다.

- [개인정보와 권한 범위](docs/PRIVACY.md): 원문 AI 전송, 이름 가림 범위, 계정별 분리, 보관·삭제의 한계
- [오류와 보완 재제출](docs/TROUBLESHOOTING.md): 미검증 앱, 401/403, 담당자 확인, 접수번호 혼동, 중복 잔존
- [검증 범위](docs/VERIFICATION.md): Studio 8사례·고정 값 88개 확인과 로컬 모의 검증의 구분

최종 Studio 설정은 **#14**입니다. 2026-11-10의 8사례 검증에서 `reason`을 제외한 정답지 고정 값 11개씩 **88개가 일치**했고, Studio UI 표시 실행 시간은 사례별 **38~49초**였습니다. 이 수치는 해당 실행 기록이며 반복 실행의 동일성·실메일 왕복 시간·대량 운영 성능을 보장하지 않습니다.

이 저장소는 API 키, OAuth 토큰, 실제 받은편지함 원문·로그, 데모 영상을 포함하지 않습니다. 별도 오픈소스 라이선스는 지정하지 않았으며, 참고한 학교 서식과 외부 서비스의 권리는 각 권리자에게 있습니다.
