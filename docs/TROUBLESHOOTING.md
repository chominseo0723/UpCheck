# 상태와 오류 해결

## Google 미검증 앱 또는 접속 차단

`Unverified`, `Authorization needed`, `Google에서 확인하지 않은 앱`은 해당 Google 앱의 검증·권한 연결과 관련된 화면입니다. 공개된 GitHub 코드, 일반 `/exec` 주소, Studio 라이브러리 승인은 Google OAuth 검증을 대신하지 않습니다.

요청 권한은 계정 소유자가 직접 확인해야 합니다. 기관 정책으로 차단된 경우 관리자에게 앱 허용 여부를 확인합니다. 외부 계정에 경고 없이 제공하려면 Google의 정식 앱 검증 등 필요한 절차를 진행해야 하며, 이 저장소는 그 완료를 주장하지 않습니다. [Google 공식 설명](https://developers.google.com/apps-script/guides/client-verification)

현재 관리자 링크는 자기 메일을 연결하는 화면입니다. 다른 사람이 접속해 기존 운영자의 접수 기록을 읽는 공개 데모가 아닙니다.

## 관리자 이메일을 바꿨는데 연결되지 않음

관리자 주소는 실제 로그인한 Google 계정과 같아야 합니다. 다른 관리자의 메일을 연결하려면 그 계정으로 접속해 Google 권한과 Upstage 연결을 마쳐야 합니다. 주소 입력만 바꿔 타인의 받은편지함을 조회할 수 없습니다.

Apps Script 배포가 **접속 사용자로 실행**인지도 확인합니다. 소유자 실행 배포는 다중 관리자 분리 전제와 맞지 않습니다.

## 처리 안내 체크 후 저장이 막힘

안내문과 API 키가 그대로이면 실행 중에도 처리 안내 확인과 자동 안내 설정을 저장할 수 있습니다. 안내문이나 키를 변경했다면 **중지 → 저장 → 다시 시작**이 필요합니다.

이전 배포의 코드가 남아 있다면 로컬 변경만으로 해결되지 않습니다. 통합 파일과 기존 배포의 새 버전 적용 여부를 확인합니다.

## 새 메일이 접수되지 않음

1. 자동 점검이 켜져 있는지 확인합니다.
2. 수신 주소가 관리자 로그인 계정과 같은지 확인합니다.
3. 제목이 정확히 **`[서류체크 실험]`**으로 시작하는지 확인합니다. `Re:` 답장 접두어는 허용합니다.
4. 관리자 자신이 보낸 메일, 초안, 휴지통 메일은 제외됩니다.
5. 설정 저장 시점 이후에 도착한 새 메일인지 확인합니다.
6. PDF 첨부가 있어야 합니다. 누적 PDF 12개·합계 20MB를 넘으면 처리 범위를 벗어납니다.
7. `지금 확인` 또는 다음 5분 자동 점검으로 접수·결과 조회를 진행합니다.

한 번의 점검은 대기 건 최대 3개를 먼저 처리하고 전체 작업 수 최대 6개까지 진행합니다. 검색은 최대 30개 대화, 저장 기록은 120개에서 신규 접수를 제한하고 화면은 최근 100개를 표시하는 실험용 구조입니다. 대규모 장기 운영에는 외부 저장소·보관 정리와 계정별 할당량 검토가 필요합니다.

## AI 점검 중에서 바로 결과가 나오지 않음

파일 업로드, AI 실행, 결과 조회는 단계가 나뉩니다. Studio 실행이 끝났어도 다음 결과 조회 전까지 화면이 진행 중일 수 있습니다. `지금 확인`으로 조회하거나 다음 점검을 기다립니다.

계속 진행 중이라면 관리자 상세 오류, Apps Script 실행 기록과 Studio 실행 상태를 확인합니다. 코드에 모든 장기 실행을 강제로 만료하는 별도 제한 시간이 있는 것은 아닙니다. Google의 실행·메일·외부 호출 [할당량](https://developers.google.com/apps-script/guides/services/quotas)도 적용됩니다.

## 누락이 있는데 담당자 확인으로 나옴

누락·중복만 확정됐을 때 자동 보완 안내를 보냅니다. 아래 항목이 함께 있으면 발송을 보류할 수 있습니다.

- `uncertain_documents`에 문서가 있음
- 작성자나 접수번호가 불명확함
- 다른 접수번호의 서류가 섞임
- 실제 제출된 필수 서명의 표시가 없거나 읽기 어려움
- 결과 형식 오류, 권한 문제 또는 복구 한도 초과

필수 동의서가 아예 빠진 것은 누락으로 안내할 수 있으며, 빠진 문서 때문에 실제 제출 문서의 `signature_status`를 무조건 누락으로 만들지 않도록 최종 #14에서 보완했습니다. `format_status: 원본 확인 필요`만으로 모든 보완 안내를 막지는 않습니다.

오류를 해결한 뒤 미발송 REVIEW 건의 **이 접수 다시 점검**을 사용할 수 있습니다. 이미 보냈거나 발송 여부가 불명확한 기록에는 이 재점검을 허용하지 않습니다.

## 보완했는데 중복이나 다른 접수번호가 남음

다른 파일명을 붙이면 기존 묶음에 **추가**됩니다. 묶음 안의 중복 페이지를 제거하려면 수정 묶음을 **원래와 같은 파일명**으로 보내야 합니다.

예를 들어 C 접수에 B용 박지민 동의서를 추가하면 C의 기존 김하늘 중복은 남고, B 동의서의 접수번호도 다르므로 담당자 확인이 됩니다. `examples/중복건_답장보완용`의 두 PDF를 파일명 그대로 C 대화에 함께 답장하면 기존 중복 묶음과 잘못 추가한 B 동의서를 각각 교체하도록 준비되어 있습니다.

첫 C 제출만 있고 B 파일을 추가하지 않은 대화에도 두 파일을 함께 사용할 수 있습니다. 합계 7페이지, 논리적 제출서류 6부가 됩니다. B 누락 대화에는 B용 파일을 사용합니다. 다른 접수번호로 파일을 섞지 않습니다.

보완 후에도 이전 행의 `보완 안내 발송`은 과거 이력으로 남습니다. 최신 `Re:` 행의 결과를 확인합니다.

## 401 또는 403

API 키 형식·유효성, 해당 워크플로우 접근 권한, 사용량·연결 설정과 대상 버전을 확인합니다. 키를 바꾸려면 중지 후 저장합니다. 재시도 대상인 미접수 연결 실패 건에는 화면의 재점검 기능을 사용할 수 있습니다.

API 키를 오류 화면이나 GitHub 이슈에 붙여 넣지 마세요. 오류 내용을 공유할 때는 키와 실제 개인정보를 제거합니다.

## 장애가 나면 다시 동작하는가

| 상황 | 코드의 처리 |
| --- | --- |
| 네트워크·429·서버 일시 오류 | 최대 3회 추가 재시도, 1·5·15분 후 재개 가능 시점 저장 |
| 이미 받은 실행 ID가 있음 | 기존 실행 결과 조회를 이어감 |
| 실행 실패·만료·형식 오류 | 제한 횟수 안에서 다시 실행 |
| 업로드 중 중단 | 저장된 파일 ID를 재사용해 남은 단계 재개 |
| 발송 응답 유실 | 발송 이력을 최대 3번 확인, 자동 재발송 안 함 |
| 권한·파일 오류 또는 반복 실패 | 담당자 확인으로 남김 |
| 더 최신 보완 메일 발견 | 이전 처리·회신을 중단하고 최신 건 우선 |

1·5·15분은 정확한 발동 시간이 아니라 재개 가능한 시점입니다. 실제 실행은 다음 5분 점검이나 `지금 확인` 때 진행되며 Google 트리거 지연도 있을 수 있습니다. 실행 생성 응답을 잃어버리면 이전 AI 작업의 ID를 알 수 없어 중복 AI 실행 가능성이 남습니다. 실행 접수 시도는 최초 포함 최대 4회입니다. 메일을 반드시 한 번 전달한다는 보장도 하지 않습니다. 중복 발송을 피하려고 불명확한 경우 사람 확인을 남기는 방식입니다.
