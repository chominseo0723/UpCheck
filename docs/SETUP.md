# 설치와 배포

## 준비물

- Gmail 또는 Google Workspace 관리자 본인 계정
- Apps Script 사용·메일 권한 연결이 허용된 기관 환경
- 실행 대상 Studio 워크플로우에 접근 가능한 Upstage 계정과 API 키
- 로컬 빌드·모의 검증용 Node.js 18 이상. 실제 웹앱 실행은 Apps Script에서 합니다.

이 저장소에는 npm 의존성이 없습니다. `npm install`이나 별도 로컬 웹 서버가 필수는 아닙니다. `src/Index.html`을 파일로 직접 열면 `google.script.run`이 없어 실제 메일·저장 기능이 동작하지 않습니다.

## 1. 배포 파일 생성

```bash
git clone https://github.com/chominseo0723/UpCheck.git
cd UpCheck
npm test
npm run check:build
```

생성 결과:

- `build/Deploy.gs`: 공통 규칙, 서버 코드와 HTML 상수가 합쳐진 파일
- `build/appsscript.json`: 실행 환경과 요청 권한

원본 파일은 `src/`에 있습니다. `build/Deploy.gs`는 빌드 결과이므로 직접 수정하지 않습니다.

## 2. Studio 연결 대상 선택

배포 예제는 아래 워크플로우를 사용합니다.

```text
WORKFLOW_ID = agt_H2fTK8CzwMhCsHeaNh9ZQy
WORKFLOW_CONFIG_VERSION = 14
```

현재 워크플로우를 사용할 수 있는 계정의 API 키가 필요합니다. 공개된 코드나 링크를 가지고 있다는 이유만으로 다른 계정에 실행 권한이 생기는 것은 아닙니다.

별도 워크플로우를 만든 경우:

1. `workflow/workflow.json`의 Parse·Classify·추출 스키마·Instruct 프롬프트·연결 설정을 참고해 Studio에서 해당 워크플로우를 구성합니다. 이 JSON은 실제 설정 내보내기 파일이며 Apps Script가 실행 중에 자동으로 가져오는 파일은 아닙니다.
2. Studio에서 해당 워크플로우를 직접 시험하고 모델 ID와 사용할 설정 버전을 확인합니다.
3. `src/Code.gs`의 `WORKFLOW_ID`, `WORKFLOW_CONFIG_VERSION`을 본인의 값으로 수정합니다.
4. 최종 출력은 `evaluation/answer.json`의 `output_keys`와 `src/Core.js`가 요구하는 형식을 유지합니다.
5. 빌드 후 로컬 검증과 본인 워크플로우의 실 API 검증을 각각 수행합니다. 고정 #14를 확인하는 기존 회귀 검증은 대상 버전 변경에 맞게 검토해야 합니다.

원본 내보내기를 보존하려면 본인 워크플로우 설정은 별도 파일로 관리하세요. `evaluation/answer.json`은 기대 결과이며 실행 코드가 답을 덮어쓰는 용도로 사용하지 않습니다.

## 3. Apps Script 프로젝트 만들기

1. [Apps Script 홈](https://script.google.com/home)에서 새 프로젝트를 만듭니다.
2. 기본 `Code.gs`의 전체 내용을 `build/Deploy.gs`로 교체합니다. 파일 이름은 `Code.gs`여도 됩니다.
3. 프로젝트 설정에서 **편집기에 appsscript.json 매니페스트 파일 표시**를 켭니다.
4. `appsscript.json`에 `build/appsscript.json`의 전체 내용을 붙여 넣습니다.
5. 저장합니다. 통합 코드와 원본 코드를 중복 추가하지 않습니다.

요청 범위는 다음과 같습니다.

| 범위 | 사용 목적 |
| --- | --- |
| `https://mail.google.com/` | Gmail 검색·첨부 읽기·원 제출자 회신·발송 기록 확인 |
| `script.external_request` | Upstage 파일 업로드·실행·결과 조회 |
| `script.scriptapp` | 본인 계정의 5분 점검 트리거 생성·삭제 |
| `userinfo.email` | 현재 관리자 계정 확인 |

Gmail 권한은 제목으로 제한된 OAuth 권한이 아닙니다. `[서류체크 실험]` 제한은 앱 코드의 처리 대상 필터입니다. 기관 운영자는 이 차이를 확인해야 합니다.

## 4. 웹앱 배포 설정

1. **배포 → 새 배포 → 유형 선택 → 웹 앱**을 선택합니다.
2. **실행 사용자**를 **웹 앱에 액세스하는 사용자**로 지정합니다.
3. 접속 범위는 실제 사용할 관리자와 기관 정책에 맞게 선택합니다. Google 계정 사용자로 넓혀도 익명 열람이나 Google 검증 면제가 되지 않습니다.
4. 배포 후 `/exec` 주소를 복사합니다. `/dev`는 편집자용 시험 주소이므로 일반 사용자 안내 주소로 쓰지 않습니다.
5. 각 관리자는 자기 Google 계정으로 접속하고 요청 권한을 직접 확인합니다.

사용자별 Gmail 접근을 전제로 하므로 **소유자 권한으로 실행하는 배포로 바꾸지 마세요.** 사용자의 입력 이메일만으로 임의 받은편지함을 조회하지 않도록 현재 로그인 계정과 일치 여부도 검사합니다. Google의 웹앱 권한 동작은 [공식 설명](https://developers.google.com/apps-script/guides/web)을 참고하세요.

새 소스의 `OWNER_EMAIL='owner@example.com'`은 초기 관리자 제한이 아닙니다. 이전 ScriptProperties를 사용자별 저장소로 옮기는 **레거시 이전 대상**만 지정하는 예시 값입니다. 새 프로젝트에는 이전할 데이터가 없어 그대로 두어도 됩니다. 실제 이전이 필요한 기존 운영자만 해당 계정으로 값을 맞추고 개인정보·키 이전 범위를 확인해야 합니다. 공개 저장소에는 기존 운영자의 실주소와 키를 넣지 않았습니다.

## 5. 연결과 시험

1. 관리자 수신 이메일에 로그인한 계정 주소를 입력합니다.
2. Studio 연결 설정을 펼쳐 API 키를 입력합니다.
3. `examples/notice.txt` 또는 실제 제출 기준 안내문을 붙여 넣습니다.
4. 개인정보 처리 안내를 확인합니다. 확인 체크는 기관의 적법한 처리 근거 확인을 대체하지 않습니다.
5. 시험 중 자동 안내 체크를 해제하면 확정 누락·중복을 미리보기로 보관합니다. 실제 시험 회신을 원할 때 켜고 저장합니다.
6. **설정 저장 → 자동 점검 시작** 순서로 실행합니다.
7. 별도 발신 계정에서 `[서류체크 실험]`으로 시작하는 제목에 가상 PDF를 첨부해 보냅니다.
8. **지금 확인**을 눌러 접수합니다. AI 실행은 비동기이므로 한 번 눌렀을 때 결과까지 완료된다고 보장하지 않습니다. 이후 자동 점검 또는 다시 확인으로 결과를 조회합니다.
9. 정상·누락·중복·보완 답장 결과를 구분해 확인합니다.

설정 저장은 notice 길이 50~25,000자와 API 키 형식을 확인합니다. API 키 문자열을 입력했다고 원격 권한까지 보장되는 것은 아니며, 실제 업로드·실행 때 401/403이 발생할 수 있습니다.

## 6. 수정·재배포·중지

- 원본 수정 → `npm test` → `npm run check:build` → 통합 파일 복사 → **배포 관리 → 수정 → 새 버전 → 배포** 순서로 적용합니다.
- 기존 배포에 새 버전을 적용하면 해당 배포의 `/exec` 주소를 유지할 수 있습니다. 새 배포를 따로 만들면 주소도 새로 발급됩니다.
- 처리 안내 확인·자동 안내 체크만 바꿀 때는 실행 중 저장할 수 있습니다.
- 안내문이나 API 키를 바꾸려면 **중지 → 변경·저장 → 자동 점검 시작** 순서로 진행합니다.
- 중지는 해당 계정의 점검 트리거를 제거하고 자동 점검을 끕니다. 이미 저장된 기록, Google 권한, Upstage 업로드를 삭제하는 기능은 아닙니다.
- 로컬 저장소 업데이트나 GitHub 업로드는 이미 운영 중인 Apps Script 배포를 자동으로 바꾸지 않습니다.

권한 연결·기관 정책 문제는 [문제 해결](TROUBLESHOOTING.md)을 확인하세요.
